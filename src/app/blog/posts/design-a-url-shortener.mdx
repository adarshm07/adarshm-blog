A URL shortener turns `https://example.com/blog/2026/10/a-very-long-path?ref=newsletter`
into `sho.rt/4uSlPp`, and redirects anyone who visits the short link. It's
the most common first system design question because the product is tiny
but the design covers most of the basics: read-heavy traffic, unique key
generation, caching, and keeping analytics off the hot path.

## 1. Requirements

**Functional**

- Create a short link for a long URL; optionally a custom alias.
- Visiting the short link redirects to the original.
- Links can expire; owners can see click counts.

**Non-functional**

- Redirects must be fast (tens of milliseconds) and highly available — a
  broken short link is a broken link everywhere it was shared.
- Keys must be unique and hard to guess in bulk.
- Click counts can be a few seconds stale.

**Out of scope**: link previews, abuse detection beyond rate limits, user
accounts beyond an owner ID. Saying what you're *not* building is part of
the answer.

## 3. API

```
POST /links            { url, alias?, expiresAt? }  → 201 { key, shortUrl }
GET  /{key}            → 302 Location: <long url>   (or 404 / 410 if expired)
GET  /links/{key}/stats → { clicks, byDay: [...] }
```

## 4. Generating keys

This is where most of the interesting choices are.

**Hash the URL** (e.g. the first 7 characters of a base-62 SHA-256). The same
URL always gets the same key, which is nice. But different URLs can collide,
so every insert needs a check-and-retry, and two users shortening the same
URL share a link — and its stats.

**Random keys.** Generate 7 random base-62 characters (3.5 trillion
possibilities) and insert with a uniqueness constraint; on the rare
collision, try again. Simple and unguessable, and it costs nothing extra
until the table is very full.

**A counter, encoded in base 62.** Unique by construction, and no collision
checks. A single global counter would be a bottleneck, so each app server
**leases a block** — say a million IDs — from a coordination service, then
hands them out locally. The downside: sequential keys are guessable, so
anyone can enumerate links. Shuffle the bits with a reversible permutation
before encoding if that matters.

Any of these works. Say which you picked and why. Counter blocks are the most
common interview answer because they scale without collisions; random keys
are the simplest to operate.

### How long should the key be?

Base 62 (`a–z`, `A–Z`, `0–9`) gives 62 choices per character:

With random keys, what matters is how full the space is. At 6 billion links
(five years of traffic) in a 3.5-trillion space, the chance a new random key
collides is about 0.17% — one retry in every ~600 inserts. That's fine. At
6 characters it would be over 10%, and every tenth create would need a
second round trip.

### Counter blocks in code

The block allocator is a single row in a database (or a key in ZooKeeper or
etcd) that each app server bumps atomically:

```sql
-- one row; each server claims the next million IDs
UPDATE id_blocks
SET next_start = next_start + 1000000
WHERE name = 'links'
RETURNING next_start - 1000000 AS block_start;
```

```javascript
const ALPHABET =
  '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';

function toBase62(n) {
  let s = '';
  do {
    s = ALPHABET[n % 62] + s;
    n = Math.floor(n / 62);
  } while (n > 0);
  return s.padStart(7, '0');
}

class KeyAllocator {
  constructor(db) { this.db = db; this.next = 0; this.end = 0; }

  async nextKey() {
    if (this.next >= this.end) {
      const { block_start } = await this.db.one(CLAIM_BLOCK_SQL);
      this.next = Number(block_start);
      this.end = this.next + 1_000_000;
    }
    // Permute before encoding so consecutive IDs don't give
    // consecutive, guessable keys.
    return toBase62(permute(this.next++));
  }
}
```

The coordination service is touched once per million links, so it's never
the bottleneck. If a server crashes mid-block, the unused IDs are simply
lost — with 3.5 trillion keys, nobody will miss them.

For `permute`, any bijection on the ID range works: multiply by a large
odd constant modulo 62⁷, or run a small Feistel network. It isn't
encryption, just enough to stop someone walking the key space by adding
one.

### Custom aliases

A custom alias like `sho.rt/launch` shares the same `key` column, so the
primary key's uniqueness constraint handles conflicts for free. Two rules
keep it safe: reserve aliases that collide with your own routes (`/api`,
`/login`, `/links`), and keep custom aliases in a character set or length
that generated keys never use — otherwise a user can claim the alias your
counter is about to produce.

## 5. Data model

One table, keyed by the short key:

```sql
CREATE TABLE links (
  key        VARCHAR(10) PRIMARY KEY,
  long_url   TEXT NOT NULL,
  owner_id   BIGINT,
  created_at TIMESTAMPTZ NOT NULL,
  expires_at TIMESTAMPTZ
);
```

The only hot query is a lookup by primary key. Nothing joins. A relational
database is fine at this scale; a key-value store (DynamoDB, Cassandra) is
also a natural fit, and makes sharding by key trivial if it's ever needed.

## 6. The two request paths

<UrlShortenerVisualizer />

**301 or 302?** A 301 (permanent) lets browsers cache the redirect, so
repeat visits never reach you — fast, but those clicks go uncounted. A 302
(temporary) brings every click back. Most shorteners choose 302 because
analytics are part of the product.

## 7. Scaling the read path

- **Cache**: a read-through cache keyed by short key, with a TTL. Popular
  links are a tiny fraction of all links, so the hit rate is very high. See
  [caching strategies](/blog/caching-strategies-explained).
- **Replicas**: cache misses go to read replicas, not the primary.
- **CDN or edge**: for very hot links, the redirect can be served from the
  edge with a short cache lifetime.
- **Negative caching**: cache "not found" too, briefly, so someone hammering
  random keys can't push every miss through to the database.

## 8. What breaks first, and what you'd do

- **A single viral link** makes one cache key very hot. Replicate hot keys,
  or keep a small in-process cache on each app server.
- **Abuse**: people creating millions of links, or links to malware. Add
  per-owner [rate limits](/blog/rate-limiting-algorithms) on creation, and
  check URLs against a blocklist asynchronously.
- **Analytics volume**: 4,000 clicks a second written one row at a time
  would dominate the database. Publish click events to a log and aggregate
  them in batches — counts a few seconds behind are fine.
- **Expiry**: don't delete in the request path. Return 410 for expired keys
  and clean up with a background job.
