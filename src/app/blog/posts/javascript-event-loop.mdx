JavaScript runs on a **single thread** — one call stack, one thing happening
at a time. And yet it fetches data, waits on timers, and reacts to clicks
without ever freezing. The machinery that makes that possible is the
**event loop**, and once you can picture it, a whole class of "why does this
log in that order?" mysteries disappears.

This post walks through the moving parts with interactive animations — hit
**Play** on each one, or step through with **Next**.

## The moving parts

Four pieces work together every time your code runs:

- **Call stack** — where functions execute. Every call pushes a frame,
  every return pops one. JavaScript only ever runs what's on top of this
  stack.
- **Web APIs** — the browser (or Node's) side of the house: timers, network
  requests, the DOM. When you call `setTimeout` or `fetch`, the *waiting*
  happens here, off the thread, not in your JavaScript.
- **Task queue** (also called the macrotask or callback queue) — where
  finished Web API work drops its callback: an expired timer, an arrived
  network response, a click handler ready to fire.
- **Microtask queue** — a separate, higher-priority queue for promise
  callbacks (`.then`, `.catch`, `.finally`), `queueMicrotask`, and the
  continuation after every `await`.

The **event loop** itself is almost embarrassingly simple: whenever the call
stack is empty, drain **all** microtasks, then run **one** task from the
task queue, then repeat. That one rule — *all* microtasks, *one* task —
explains nearly every ordering puzzle in JavaScript.

## The classic puzzle: setTimeout vs Promise

Here's the snippet that shows up in every JavaScript interview:

```javascript
console.log("start");

setTimeout(() => {
  console.log("timeout");
}, 0);

Promise.resolve().then(() => {
  console.log("promise");
});

console.log("end");
```

Before scrolling further — what order do the four logs appear in? The timer
is `0` milliseconds, and the `setTimeout` line comes *before* the promise
line, so `timeout` before `promise`... right? Watch what actually happens:

The output is `start`, `end`, `promise`, `timeout`, because:

1. Synchronous code always finishes first — the whole script is itself a
   task, and nothing else can run until the stack is empty.
2. A `0` ms timer doesn't mean "run now", it means "put my callback in the
   task queue as soon as possible". It still has to wait its turn.
3. When the stack empties, microtasks beat tasks — the promise callback cuts
   in line ahead of the timer callback, no matter which was scheduled first.

The split matters because the two queues have different priorities, so it's

The "drained fully" part has a sharp edge: because the loop empties the
entire microtask queue before moving on — including microtasks queued *by*
microtasks — a promise callback that keeps scheduling another one will
**starve** the task queue forever:

```javascript
function loop() {
  Promise.resolve().then(loop); // freezes the page: timers, clicks,
}                               // and rendering never get a turn
loop();
```

Swap the `.then` for a `setTimeout` and the same pattern is harmless — each
iteration becomes a task, and the browser gets to render and handle input
between tasks.

## async/await is the event loop in disguise

`async`/`await` doesn't add any new machinery — it's promise callbacks with
better ergonomics. The key mental model: an async function runs
**synchronously until the first `await`**, then suspends, and its
continuation is scheduled as a microtask when the awaited promise settles.

```javascript
async function loadUser() {
  console.log("loading");
  const user = await Promise.resolve("Ada");
  console.log("hello", user);
}

console.log("A");
loadUser();
console.log("B");
```

<EventLoopVisualizer scenario="async-await" />

The order is `A`, `loading`, `B`, `hello Ada`. The surprise for most people
is `loading` before `B`: calling an async function is *not* deferred — the
body runs immediately, on the caller's stack, right up to the `await`. Only
the code *after* the `await` waits for a microtask turn. Every `await` in a
function is a potential "someone else's code runs here" gap, which is worth
remembering when you're reasoning about shared state.

## Things that bite in practice

**A 0 ms timer is a request, not a guarantee.** The delay is a *minimum*.
The callback can't run until the stack is clear and every earlier task and
microtask has finished. Browsers also clamp nested timers (typically to
~4 ms after a few levels deep), and background tabs get throttled far more
aggressively.

**Blocking the stack blocks everything.** There's no preemption: a
long-running synchronous loop holds the one thread, so clicks queue up
unhandled and rendering stalls — the classic frozen page.

```javascript
button.addEventListener("click", () => {
  const end = Date.now() + 3000;
  while (Date.now() < end) {} // page is dead for 3 seconds
});
```

For genuinely heavy computation, the options are chunking the work across
tasks (`setTimeout`, or `scheduler.yield()` in newer browsers) so the loop
can breathe between slices, or moving it off the thread entirely with a
Web Worker.

**Rendering happens between tasks.** The browser can repaint after a task
finishes (and its microtasks drain), but never in the middle of one. If you
update the DOM twice in the same synchronous block, the user only ever sees
the final state — the intermediate frame never had a chance to paint.

## A harder puzzle

Once the basic rule is solid, this one tests it:

```javascript
console.log(1);

setTimeout(() => {
  console.log(2);
  Promise.resolve().then(() => console.log(3));
}, 0);

Promise.resolve().then(() => {
  console.log(4);
  setTimeout(() => console.log(5), 0);
});

queueMicrotask(() => console.log(6));

(async () => {
  console.log(7);
  await null;
  console.log(8);
})();

console.log(9);
```

Replay the queues:

1. Synchronous code: `1`, then the async function runs up to its `await`
   (`7`), then `9`. Queued so far — tasks: [timeout A]; microtasks:
   [then-4, micro-6, after-await-8].
2. Drain microtasks in order: `4` (which schedules timeout B), `6`, `8`.
3. Take one task, timeout A: `2`, which queues a microtask; drain it: `3`.
4. Take the next task, timeout B: `5`.

Output: `1 7 9 4 6 8 2 3 5`. The `3` printing before `5` is the rule in
action — microtasks queued *during* a task run before the next task, even
one that was scheduled earlier.

## Where rendering and requestAnimationFrame fit

In a browser, one turn of the loop looks roughly like this:

1. Run one task.
2. Drain all microtasks.
3. If it's time to render (typically about every 16 ms on a 60 Hz
   display): run `requestAnimationFrame` callbacks, then compute style,
   layout and paint.
4. Repeat.

That's why `requestAnimationFrame` is the right place for visual updates:
it runs once per frame, just before the browser paints, so a change made
there is shown in the very next frame and never wasted on a frame that
isn't drawn. A `setTimeout(fn, 16)` loop drifts out of step with the
display and can run twice in one frame or skip one. See
[requestAnimationFrame and smooth animation](/blog/request-animation-frame-and-smooth-animation)
and [the rendering pipeline](/blog/rendering-pipeline-reflow-repaint).

## Node's event loop has phases

Node's loop (provided by libuv) is the same idea with more structure.
Each turn moves through phases, each with its own queue:

      ['pending callbacks', 'some deferred system-level I/O callbacks'],
      ['poll', 'new I/O events — most of your callbacks run here; waits here when idle'],
      ['check', 'setImmediate callbacks'],
      ['close callbacks', "close events, e.g. a socket's 'close'"],
    ],
  }}
/>

Between every callback, Node drains two microtask-like queues: first
everything queued with `process.nextTick`, then promise microtasks. That
makes `nextTick` even higher priority than promises — and just as able to
starve the loop if used recursively.

Two consequences come up often:

```javascript
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// From the main module: order is not guaranteed — it depends on
// whether 1 ms has elapsed when the loop first checks timers.

fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// Inside an I/O callback: always 'immediate' first, because the
// check phase comes right after poll, before timers come round again.
```

## Blocking the loop on the server

In a browser, a blocked loop freezes one user's tab. In Node, it freezes
*every* request the process is handling. The usual culprits:

- `JSON.parse` / `JSON.stringify` on multi-megabyte payloads.
- Synchronous APIs left in request paths: `fs.readFileSync`,
  `crypto.pbkdf2Sync`, `zlib.gzipSync`.
- Regular expressions with catastrophic backtracking on user input — see
  [regex backtracking and ReDoS](/blog/regex-backtracking-and-redos).
- Large loops over in-memory data — sorting a million items per request.

The asynchronous versions of `fs`, `crypto` and `zlib` hand work to libuv's
thread pool, freeing the loop. For your own CPU-heavy code, use
`worker_threads` (Node) or [Web Workers](/blog/web-workers-off-the-main-thread)
(browsers), or split the work into chunks that yield between them.

### Measuring it

You can't fix what you can't see. Node exposes event-loop delay directly:

```javascript
import { monitorEventLoopDelay } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  console.log('event loop p99 delay (ms):', h.percentile(99) / 1e6);
  h.reset();
}, 10_000);
```

A healthy server shows a p99 of a few milliseconds. Spikes to hundreds of
milliseconds mean something is blocking, and every request in flight is
waiting on it. In the browser, the Performance panel marks **long tasks**
(over 50 ms) in red, and the Long Animation Frames API reports them from
real users.

## Follow-up questions, answered

**"Is JavaScript really single-threaded?"** Your JavaScript runs on one
thread per realm — the page's main thread, or one per worker. The runtime
around it is not: the browser's network stack, Node's libuv thread pool
and the operating system do the waiting and much of the I/O in parallel.
Single-threaded *execution*, multi-threaded *platform*.

**"Why doesn't `await` block the thread?"** Because it doesn't wait in
place. It returns control to the caller, and the rest of the function is
registered as a callback to run as a microtask when the promise settles.
The thread is free in the meantime — see
[async/await under the hood](/blog/async-await-under-the-hood).

**"What's the difference between `setTimeout(fn, 0)` and
`queueMicrotask(fn)`?"** The microtask runs before any rendering or other
task — still within the current turn. The timeout runs at the earliest in
a later turn, after the browser has had a chance to render and handle
input. Use microtasks for "right after this code, before anything else";
use a task when you want to yield to the browser.

**"Why does my UI update only after a long function finishes?"** Rendering
happens between tasks. DOM changes made during one long task are batched
and painted afterwards. To show progress during long work, split it into
tasks — or move it to a worker.

**"What's `scheduler.yield()`?"** A newer browser API that pauses an async
function, lets the browser handle pending input and rendering, then
resumes — with priority over other queued tasks, unlike a plain
`setTimeout`. It's the cleanest way to break up long work on the main
thread where supported:

```javascript
async function processAll(items) {
  for (const [i, item] of items.entries()) {
    process(item);
    if (i % 100 === 0 && globalThis.scheduler?.yield) await scheduler.yield();
  }
}
```

**"Do promises run in parallel?"** No — the *waiting* overlaps, the
JavaScript doesn't. `Promise.all([fetchA(), fetchB()])` starts both
requests before awaiting either, so the network work happens concurrently,
but their `.then` callbacks still run one at a time on the single thread.
Concurrency of I/O, not parallelism of code — which is exactly why the
event loop model is enough to reason about it. See
[promises in depth](/blog/javascript-promises-in-depth).

## Wrap-up

The whole model fits in one sentence: *run the stack dry, drain every
microtask, take one task, repeat*. From that single rule you can derive why
`promise` beats `timeout`, why an async function starts synchronously, why
recursive microtasks freeze a page while recursive timers don't, and why a
busy loop kills rendering. Next time an ordering puzzle shows up in a code
review or an interview, don't memorize the answer — replay the queues. And
when a page stutters or a Node server's latency spikes for no visible
reason, measure the loop before anything else: a blocked loop explains more
mysterious slowness than any other single cause.
