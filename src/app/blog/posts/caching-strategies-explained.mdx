"Just add a cache" is the easy part of scaling a read-heavy system. The
hard part is deciding **when** the cache gets filled and **how** it stays
consistent with the database once writes happen — and different answers
to that question produce genuinely different systems, not just
implementation details. The three dominant strategies — cache-aside,
write-through, and write-back — each make a different trade between
write latency, read latency, and the risk of serving stale data.

## Why caches work at all

A cache helps only because access is skewed. If every item were read
equally often, a cache holding 10% of the data would serve about 10% of
reads. Real traffic is nothing like that: a small set of hot items — the
home page, today's posts, popular products — gets most of the reads. That
skew is what lets a cache holding a few percent of the data absorb 90% or
more of the traffic.

database:

## Cache-aside (lazy loading): the application drives the cache

The application checks the cache first; on a **miss**, it reads from the
database and populates the cache for next time. The cache never talks to
the database directly — it's the application code that owns the whole
flow.

```javascript
async function getUser(id) {
  let user = await cache.get(`user:${id}`);
  if (user) return user; // cache hit

  user = await db.query("SELECT * FROM users WHERE id = ?", [id]);
  await cache.set(`user:${id}`, user, { ttl: 300 }); // populate for next time
  return user;
}

async function updateUser(id, changes) {
  await db.update("users", id, changes);
  await cache.delete(`user:${id}`); // invalidate — don't try to update the cache in place
}
```

**Invalidate, don't update, on writes.** The tempting alternative —
writing the new value directly into the cache after a database update —
is a race-condition trap: two concurrent writes can interleave such that
the cache ends up holding the *older* value even though the database has
the newer one. Deleting the key and letting the next read repopulate it
from the database sidesteps that race, at the cost of one extra cache
miss.

- **Pro:** only requested data ever enters the cache — no wasted memory on
  data nobody reads. Cache failure degrades gracefully to "every request
  hits the database," rather than breaking writes.
- **Con:** the first request for any key always misses (cold-cache
  latency), and there's a window between a write and the next read where
  a naive read-through-cache-only client could serve stale data if
  invalidation is missed or delayed.

### The race that delete-on-write doesn't fix

Deleting on write removes the write-write race, but a read-write race
remains:

1. Reader misses the cache and reads `v1` from the database.
2. Writer updates the database to `v2` and deletes the cache key.
3. Reader, slower, now writes its `v1` into the cache.

The cache holds `v1` until the TTL expires. It's rare — the reader has to
be slower than an entire write — but at high traffic, rare things happen
every day. Defences, from cheapest:

- **A TTL on everything.** It bounds how long any stale value can live.
  This alone is enough for most data.
- **Delayed second delete.** The writer deletes again a second or so
  later, cleaning up anything a slow reader wrote in between.
- **Versioned writes.** Store a version with each value, and only write to
  the cache if the version is newer than what's there (`SET` only if
  greater, via a small Lua script in Redis).
- **Leases.** On a miss, the cache hands the reader a token; a delete
  invalidates outstanding tokens, so the slow reader's late `SET` is
  rejected. Memcached at large scale popularised this.

### Invalidation from the database itself

Every write path having to remember `cache.delete` is fragile — one
forgotten admin script and the cache is wrong. An alternative is to drive
invalidation from the database's change stream (change data capture): a
consumer reads committed changes and deletes the matching keys. Writes
can't forget, and invalidation happens only after commit. The cost is a
little extra delay and another moving part. It's the same idea as the
[outbox pattern](/blog/dual-writes-and-the-outbox-pattern): don't trust two
separate writes to stay in sync.

## Read-through: the cache loads for you

Read-through is cache-aside moved into a library or the cache itself: the
application only ever calls `cache.get(key)`, and on a miss the cache calls
a loader function to fetch from the database. The behaviour is the same as
cache-aside; the difference is that the loading logic lives in one place
instead of every caller, which makes it the natural place to add
stampede protection.

## Write-through: the cache is updated in lockstep with the database

Every write goes through the cache, which updates itself and the database
**synchronously**, together, before the write is considered complete.

```javascript
async function updateUserWriteThrough(id, changes) {
  const updated = await db.update("users", id, changes);
  await cache.set(`user:${id}`, updated); // cache and DB updated together, in the write path
  return updated;
}
```

- **Pro:** the cache is never stale — a read right after a write always
  sees the new value, because the cache was updated as part of the write
  itself.
- **Con:** every write now pays the latency of **two** operations (cache
  write plus database write) instead of one, and data that's written but
  never read still occupies cache space — write-through caches everything
  that's written, not just what's requested.

Write-through is still exposed to the write-write race if two writers
update the same key concurrently and their cache writes land out of
order. Versioned writes fix that, as above.

## Write-back (write-behind): the cache absorbs writes, the database catches up later

Writes go to the cache **only**, immediately returning success, and the
cache asynchronously flushes changes to the database later — either on a
timer or when a slot needs to evict.

```javascript
async function updateUserWriteBack(id, changes) {
  await cache.set(`user:${id}`, { ...changes, dirty: true });
  return { success: true }; // returns before the DB write happens
  // a background worker periodically flushes dirty entries to the database
}
```

- **Pro:** write latency is as fast as the cache itself — the database's
  latency is completely removed from the write's critical path. This also
  lets you **batch and coalesce** writes: ten rapid updates to the same
  key become one database write instead of ten.
- **Con:** genuinely risky — if the cache crashes or the process dies
  before the flush happens, unflushed writes are **lost**, because the
  cache was the only place they existed. This strategy is only appropriate
  when the cache has its own durability (persistence, replication) or the
  data can tolerate loss.

A view counter is the textbook good fit: losing a few seconds of
increments is harmless, and coalescing a million `+1`s into one `UPDATE`
a second is a huge saving.

## Refresh-ahead: never let hot keys expire

For keys that are read constantly, the moment of expiry is a hazard: the
next request pays the full database latency, and if many requests arrive
together, they all do. Refresh-ahead reloads a key in the background
*before* it expires — for example, when a read finds less than 20% of the
TTL remaining. Readers keep getting the cached value; the refresh happens
off the request path.

The trade-off is wasted refreshes for keys that weren't going to be read
again. Use it for a known-hot set (configuration, home page fragments),
not for everything.

## TTLs and eviction

**TTL** answers "how stale may this be?" and is a product decision as much
as a technical one. A user's display name can be minutes stale; a price in
a checkout flow cannot. Two practical rules:

- **Add jitter.** If a batch job warms 100,000 keys with the same TTL, they
  all expire in the same second. A random ±10% spreads expiry out.
- **Cache misses briefly.** Cache "not found" for a short TTL (negative
  caching), or a client hammering nonexistent IDs sends every request to
  the database.

**Eviction** answers "what goes when memory is full?":

- **LRU** (least recently used) evicts what hasn't been touched longest —
  a good default. See [LRU cache from scratch](/blog/lru-cache-from-scratch).
- **LFU** (least frequently used) keeps items that are popular over time,
  and resists one big scan pushing everything useful out.
- **TTL-based** eviction removes the soonest-to-expire first.

Redis exposes these as `maxmemory-policy` (`allkeys-lru`, `allkeys-lfu`,
`volatile-ttl`, and others). Choose deliberately: the default in many
setups is `noeviction`, which makes writes fail when memory fills up.

## Where caches live

A request can hit several caches before reaching the database, and each
layer has a different scope:

- **Browser** — per user, controlled by
  [HTTP caching headers](/blog/http-caching-headers).
- **CDN** — per region, for public responses and assets; see
  [CDNs](/blog/cdn-explained).
- **In-process** — a small map inside each app server. Fastest possible,
  but every server has its own copy, so invalidation has to reach all of
  them; keep TTLs short.
- **Distributed cache** (Redis, Memcached) — shared by all app servers; the
  usual home for cache-aside.
- **Database buffer pool** — the database caching its own pages in memory.
  Often why a "cold" query is slow once and fast afterwards.

A common pattern for very hot keys is two tiers: a tiny in-process cache
with a TTL of a few seconds in front of the distributed cache. It removes
the network hop for the hottest items and protects the cache node that
owns them.

## When the cache hurts

- **Stampedes.** A hot key expires and thousands of requests miss at once,
  all querying the database. Fix with request coalescing (one loader per
  key), refresh-ahead, or stale-while-revalidate — see
  [cache stampedes](/blog/cache-stampede-and-thundering-herd).
- **Cold starts.** After a deploy or a cache restart, the hit rate is zero
  and the database takes full load. Warm critical keys before taking
  traffic, or ramp traffic gradually.
- **Hidden dependency.** If the database can no longer handle traffic
  without the cache, the cache isn't an optimisation any more — it's
  critical infrastructure, and needs replication and capacity planning
  like any database.

## Picking one

- **Cache-aside** is the default for most read-heavy web applications —
  Redis or Memcached in front of a relational database, populated
  on-demand. It's forgiving of cache outages and doesn't cache data nobody
  asked for.
- **Write-through** earns its extra write latency when read-after-write
  freshness matters more than write speed — session state, user-facing
  data where "I just saved this and it shows the old value" is a visible
  bug.
- **Write-back** is reserved for cases where write throughput is the
  bottleneck and the cache itself is durable enough to trust — counters,
  some storage engines, and systems explicitly built with replication or a
  write-ahead log underneath the cache tier to eliminate the data-loss
  risk.
- **Refresh-ahead** is an add-on for a known-hot set of keys.

They're also not mutually exclusive within one system — it's common to
use cache-aside for most entities and write-through specifically for the
handful of fields where staleness would be user-visible.

## Wrap-up

The question a caching strategy actually answers isn't "should I cache
this," it's "when does the cache get populated, and what happens to the
database on a write." Cache-aside keeps writes cheap and the cache lean at
the cost of occasional stale reads; write-through keeps the cache always
fresh at the cost of slower writes; write-back makes writes nearly free by
deferring the database entirely, at the cost of real data-loss risk if the
cache fails first. Whichever you choose, put a TTL on everything, watch the
hit rate, and plan for the day the cache is empty.
